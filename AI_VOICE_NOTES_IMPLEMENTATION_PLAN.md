# AI Voice Notes - Sequential Implementation Plan

**Product:** Local, single-user Czech voice-notes proof of concept. **Code and documentation:** English. **UI, voice commands, and user-facing errors:** Czech. **Target:** Linux/WSL with Docker, local Chromium, microphone, and optional paid provider accounts. This document specifies implementation work; it does not authorize a paid API request.

## 1. Execution Contract

- P01-P54 plus the separately numbered P07B, P13B, P19B, P30B, P41B, and P42B are the **60 core phases**, in order (a `B` phase immediately follows its same-numbered phase); P55, P55B, P56, P56B are optional and follow P54. **One phase ID is one coding-agent assignment**, including every `B` phase. Implement only the first unapproved phase, run its checks, report it, and stop for the user's explicit acceptance. Do not initialize Git, commit, seed, migrate the user's database, or call a paid provider merely because a phase mentions those actions.
- Every `Pass` below is independently testable at the end of that phase, using only earlier phases. Add the named test file in that phase, not in a later regression phase. For pure/server-only phases, the manual acceptance step is to run the named deterministic command and inspect its listed assertions; do not invent a UI that belongs to a later phase. Record an approved phase, evidence, and any authorized deferral in `docs/PROGRESS.md` **only after** the user responds.
- States: `Implemented / accepted` requires deterministic checks and the user's acceptance; `Mock verified / live unverified` means the deterministic implementation was accepted but a separately authorized real-provider check has not happened; `Blocked` means a concrete incompatibility, missing required environment, or failed acceptance test. An unverified live check may be deferred by explicit user approval for subsequent **mock-only** implementation, but it never counts as real-provider acceptance or enables an unverified live feature. A demonstrated incompatible API blocks its dependent phases until the user approves a revised contract. Do not silently switch providers, models, transports, or SDKs.
- Once scripts exist, run `pnpm lint`, `pnpm typecheck`, and `pnpm test` after each code phase; run `pnpm build` for Next.js changes; run `pnpm test:db` for DB changes and `pnpm test:e2e` for affected completed browser flows. All of these are deterministic, use dummy provider responses, and **never** spend money. Phase-specific `Pass` checks are additional. Live smokes require a separate request to and authorization from the user, and belong in `docs/PROVIDER_SMOKE_TESTS.md`.
- Use strict TypeScript, Zod at external boundaries, small services, bound request size/time/count, and inspect installed SDK types and current primary vendor documentation before integration. No abstract agent framework, paid Tiptap Conversion, Redis, background workers, multi-user auth, public deployment, automatic AI edits, or fabricated provider response. Do not put **real user** note contents, audio, tokens, full model prompts, or API keys in logs, test artifacts, Git, URLs, or analytics; synthetic fixture text belongs only in tests/seed.
- Report after each phase: number/state, files changed, observable behavior, exact commands/results, manual acceptance steps, any deferred live check, and the next phase. End the report with **"Otestujte nyní, zda…"** and the phase's manual steps; then stop.

### Persistence, concurrency, and approval contracts

- `notes`: UUID PK, `seed_key TEXT NULL UNIQUE` (server CLI only), title, canonical `content_md`, derived `content_plain`, nullable category, integer `version` starting at 1, UTC `created_at`/`updated_at`, nullable `deleted_at`. Active list orders by `(created_at DESC, id DESC)`, default 10/page; deleted notes are excluded except in Trash. DB timestamps, not browser clocks, determine updates except the explicitly backdated seed.
- `note_revisions`: UUID, note FK `ON DELETE CASCADE`, unique `(note_id, note_version)`, reason (`initial`, `manual`, `voice`, `ai`, `undo`, `restore`, `metadata`), UTC time, and exact **before/after** snapshots of `{title, contentMd, category, tags}`. The initial snapshot is version 1. Draft autosaves increment note version but do not create a history item for each keystroke; named saves, dictated changes, metadata approvals, accepted AI patches, undo, and restores do. Deletion/restoration is versioned; no edit silently overwrites a concurrent edit.
- Every content/metadata mutation takes `expectedVersion`; update with compare-and-swap and add a named revision in the **same DB transaction** when applicable. `0` changed rows means HTTP 409 with latest version and no mutation. Undo of a named operation uses its saved **before** snapshot only if the current note version still equals that operation's applied version. Restoring an older snapshot uses an explicit preview and current version. Never infer the prior state from the previous revision because intervening autosaves may exist.
- `note_tags`: `(note_id, tag)` PK, FK `ON DELETE CASCADE`; tags/category live in the snapshot above. `note_chunks`: note FK `ON DELETE CASCADE`, note version, ordinal, text, nullable `vector(1536)`, model/status; unique `(note_id, note_version, chunk_index)`. `ai_usage`: operation/provider/model, started/settled/unknown status, reserved estimated maximum, nullable provider usage and reported cost, UTC time. Related seed-owned rows must cascade on CLI seed replacement; ordinary deletion is soft.
- All AI changes are **proposals**. A provider returns only a Zod-validated narrow operation, never executable SQL, Markdown offsets, or an entire replacement note. A deterministic resolver makes a version-bound diff; only a separate user's on-screen confirmation applies it once. Note text is untrusted prompt data. Voice-agent model tool calls can create proposals but cannot provide the approval credential or approve them.
- Before any billable operation, display provider/model, bounds, estimated or unknown cost, and require that operation's deliberate user action. `AI_REQUEST_BUDGET_USD` is an **app-side estimated admission budget**, not a hard billing limit; one DB transaction reserves an upper estimate before an outbound request and reconciles actual usage when available. Unknown/ambiguous charges stay unknown, not `$0`; no automatic replay of an uncertain request. Never reset budget merely by restarting. A realtime browser session cannot be cut off by an exact dollar threshold: cap session duration, show the caveat, and recommend a provider-side spending limit.
- Microphone ownership is exclusive across same-origin tabs through Web Locks (supported Chromium); a shared client controller arbitrates dictation, optional TTS stop listening, and conversation. If Web Locks are unavailable, disable microphone features with a Czech explanation rather than risk simultaneous hidden recording. Stop and unmount release tracks, locks, and audible output. No background listening; never persist raw microphone audio or conversational transcripts by default.
